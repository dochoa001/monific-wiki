Es el mismo flujo de creación de deals que la compra individual, pero ejecutado en lote por el servidor. Deals generados: 1 deal PURCHASE por cada usuario que compró exitosamente. Mismas propiedades que la compra individual. Se procesan secuencialmente (no en paralelo). Mercado Secundario — Compra por Precio Un usuario compra participaciones en venta de otros usuarios desde la app de Monific. El sistema selecciona automáticamente los vendedores con participaciones al precio solicitado. Deals generados:  Deal Para quién Etapa Descripción 1 deal SOLD por cada vendedor Vendedor Mercado secundario (1059885878) Cada vendedor involucrado recibe su propio deal de venta 1 deal PURCHASE acumulado Comprador Inversión activa (1035451748) Un solo deal con el monto total realmente comprado  Ejemplo: Si María compra 100 participaciones y estas se obtienen de 3 vendedores diferentes (Pedro: 40, Ana: 35, Luis: 25): Se crean 3 deals SOLD (uno para Pedro, uno para Ana, uno para Luis) con sus montos individuales Se crea 1 deal PURCHASE para María con el monto total Mercado Secundario — Compra Directa (Usuario a Usuario) Un usuario compra participaciones directamente de un vendedor específico desde la app de Monific (transacción dirigida). Deals generados: Idéntico al flujo 5.3, pero el vendedor siempre es el mismo usuario. Este hash sirve para: Identificar si un movimiento ya fue reportado (mismo hash = duplicado) Identificar cambios en datos existentes cuando el hash almacenado difiere del nuevo El servidor interno usa estos hashes en su reconciliación periódica  Propiedades incluidas en el hash (ordenadas alfabéticamente):  # Propiedad 1 amount 2 clave_de_desarrollador 3 closedate 4 dealname 5 monto_invertido 6 motivo_de_interes 7 move_type 8 nombre_de_proyecto 9 technical_source  Propiedades excluidas del hash: pipeline, dealstage (metadatos), move_id (clave de lookup), monific_last_synced_at (cambia en cada sincronización). Clave de Deduplicación El campo move_id es el identificador único del movimiento de participaciones. Si dos deals tienen el mismo move_id, representan el mismo movimiento. El sistema almacena esta relación en la base de datos para prevenir la creación de deals duplicados. Manejo de Errores y Resiliencia Deals — Fire-and-forget Los deals se envían a HubSpot de forma asíncrona sin esperar respuesta. Si HubSpot está caído, tiene rate limiting o cualquier otro error: La compra/venta de participaciones se completa exitosamente en Monific El error se registra en los logs del servidor El servidor interno reconcilia los deals faltantes en su próxima ejecución batch Contactos — Secuencial con tolerancia a fallos A diferencia de los deals, la creación y actualización de contactos es secuencial: el flujo espera la respuesta de HubSpot antes de continuar. Sin embargo, si HubSpot falla: El registro del usuario continúa normalmente (el error se captura internamente) Se registra el error en logs El contacto se puede crear o actualizar manualmente después Propiedades Custom de HubSpot Para el listado completo de propiedades personalizadas requeridas en cada objeto de HubSpot, consultar la sección 14.  	 Diagrama de Flujo del Ciclo de Vida No crea ni actualiza propiedades de contacto — solo crea el mapeo interno (relación User → HubspotContact en Neo4j). Criterio: Usuarios que tengan cartera STP creada y aún no tengan mapeo HubSpot. Sincronización de Deals de Inversión Cuándo se ejecuta: Batch manual vía POST /hubspot/investors/deals/sync. Propósito: Crear/actualizar deals para todos los movimientos de participaciones Es una duplicación intencional para compatibilidad con diferentes vistas y reportes. technical_source es siempre "batch". Es una constante fija necesaria para el sistema de sincronización y no debe cambiarse. closedate es un timestamp Unix en milisegundos (no una fecha legible). HubSpot lo interpreta automáticamente como fecha. motivo_de_interes tiene dos valores posibles: "Invertir en proyectos" (inversionistas) y "Solicitar Financiamiento" (desarrolladores). Reglas de pipelines y deduplicación Dos pipelines separados: 708176204 es exclusivo para inversiones. El pipeline default es para campañas de fondeo. No deben mezclarse. Pipeline y stage no se modifican en actualizaciones: Una vez creado, las sincronizaciones solo actualizan propiedades de negocio. Claves de deduplicación: move_id para deals de inversión, numero_de_proyecto para deals de campañas. Deals SOLD y PURCHASE del mercado secundario son independientes entre sí, pero ambos se asocian al mismo deal de campaña. Arquitectura y resiliencia Las liquidaciones las genera el servidor interno de Monific mediante proceso batch, no la app. Los usuarios tienen un único rol: cada usuario es inversionista o representante legal, nunca ambos. Red de seguridad: si un deal no se creó en tiempo real, el servidor interno lo crea en su próxima ejecución batch.  	 Glosario  Término Definición Participación Unidad de inversión en una campaña de fondeo.
